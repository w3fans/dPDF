## Proposed implementation and checks

Render keys identify document/page, full raster dimensions, view rotation and
region; request envelopes carry view generation to cancel stale work. Native
PDFium objects remain on the existing owner thread. Use a small destination
bitmap with a negative native origin and the form-data render path; matrix/clip
configuration would disable form-field rendering. No flattening or document
mutation is permitted. Existing layout/transforms continue to place selections,
search results, marks and review overlays.

Cover complete tile coverage, bounded overscan/bytes, fractional viewport edges,
all rotations, crop offsets and UserUnit; compare stitched detail with an exact
full reference including forms/annotations. Qualify rapid pan/zoom/tab changes,
stale completion rejection, native landmarks, memory plateau and ordinary-path
performance. Required hosted native/compiler/runtime checks remain pending; no
local Rust/C++ compilation.

## Development implementation

The draft includes a bounded viewport planner, 510-pixel tile cores with one-pixel
gutters and native negative-origin rendering into small bitmaps. Eight global
permits cover queued/active render work and unconsumed replies across generation
changes. Detail is layered below selections/search/mark/review overlays without
changing their document transforms. Generated source contracts and formatting
are checked locally; compilation and native execution use hosted public CI.

New native diagnostics compare 72 generated full-transform/stitch cases and
exercise real windows in twelve view/rotation combinations at scale 1/1.5/2,
including panning, rapid zoom generations and tab switch/closure. Their presence
is not a passing result. GUI latency, memory plateau, ordinary-path regression
comparison and operator acceptance remain pending until measured.
